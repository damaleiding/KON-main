# KVA

`KVA` 是一个面向小说创作的 AI 协作工程。它不是单一应用仓库，而是把作品规则、设定、正文、分支稿、提示词、账本、索引和可复用写作方法论放在一起，方便在本机和 GitHub 之间同步可协作的事实层。

这个工作区的核心目标是服务小说创作中的世界观与角色设定、长篇正文写作、章节润色、分支改写、伏笔管理、发布稿整理和多窗口协作，让不同任务窗口可以围绕同一套文件事实层协作，而不是依赖单个聊天窗口的历史上下文。

## 当前定位

| 区域 | 作用 |
| --- | --- |
| `AGENTS.md` | 工作区最高层核心规则，只保留最通用、最必要的约束和扩展规则索引。 |
| `docs/` | 工作区级长期文档、架构说明、同步策略、周报、交接资料和高优先级扩展规则。 |
| `methods/` | 可复用写作方法论，例如长篇规划、章节拆分、润色流程、分支合并和发布整理。 |
| `projects/` | 具体小说项目或作品集，每个项目保存自己的规则、设定、正文、分支、账本和工作流。 |
| `tools/` | 工作区级可复用工具，例如启动简报、账本、索引、文本拆分、批量替换和发布整理脚本。 |
| `references/` | 跨项目参考入口。项目专属参考资料优先放到各项目自己的 `refs/`。 |
| `templates/` | 新项目模板、Prompt 模板、账本模板、章节模板、角色卡模板和交接模板。 |

## 协作方式

默认原则是：文件系统负责存储，不等于每次对话都要整仓读入上下文。新的工作应该先通过轻量入口和索引找到最小事实源，再进入具体任务。

推荐节奏：

1. 先读取根目录 `README.md` 和 `AGENTS.md`，确认工作区目标和核心规则。
2. 如果任务属于具体项目，进入 `projects/<project-name>/`，优先读取该项目的 `PROJECT.md` 和 `WORKFLOW.md`。
3. 如果任务需要细则，按主题读取 `docs/agent-rules/` 下的高优先级扩展规则。
4. 通过项目的 `_pipeline/`、`_ledger/`、`refs/_index/` 或 `prompts/` 定向查找事实。
5. 生成、改写或润色文本后，把 prompt、参考输入、模型、输出路径、版本和筛选结论写回项目事实层。
6. 重要产物通过账本、索引和审稿记录收口，不依赖聊天历史长期保存。
7. GitHub 只同步规则、代码、文档、索引、Prompt、账本、manifest 等核心事实层；大型媒体和临时输出走外部同步或本地管理。

工具约定：

- 字数统计、章节长度、全文长度和稿件长度对比必须使用 `tools/word-count/`，默认按非空白 Unicode 字符统计，不用模型估算。

## Agent 规则分层

`AGENTS.md` 只放最高优先级核心规则。更细的规则放在 `docs/agent-rules/`：

- `project-structure.md`：目录、项目入口、HTML 项目纲要、索引和账本职责。
- `ai-production.md`：AI 写作、prompt、参考资料、审稿和生产记录。
- `subagent-collaboration.md`：Claude / DeepSeek 子 Agent 使用规则。
- `git-security.md`：Git 同步边界、安全隐私、媒体和临时输出处理。
- `writing-and-modification.md`：语言命名、修改联动、新项目和新工具规则。

## 推荐项目结构

每个具体项目建议放在 `projects/` 下：

```text
projects/<project-name>/
  AGENTS.md
  PROJECT.md
  WORKFLOW.md
  <project-name>_project-brief.html
  _pipeline/
  _ledger/
  docs/
  refs/
  prompts/
  outputs/
  review/
  trash/
```

建议含义：

- `PROJECT.md` 保存项目记忆，包括目标、世界观、风格方向、角色锚点、作品范围和待确认问题。
- `WORKFLOW.md` 保存工作流，包括启动方式、生成节奏、审稿方式、收口动作和交接格式。
- `<project-name>_project-brief.html` 保存给人类看的静态项目纲要，必须和 `PROJECT.md` 同级，用来快速理解项目目标、作用、资产状态、关键入口和下一步。
- `_pipeline/` 保存项目级工具索引、上下文路由和技能触发规则。
- `_ledger/` 保存生产账本、prompt 索引、审稿决策、版本流转和 manifest。
- `refs/` 保存外部参考、风格参考、资料摘录和治理索引。
- `prompts/` 保存可复用提示词、角色提示词、润色提示词和正式写作提示词。
- `outputs/` 保存生成、改写、导出或发布前整理结果。
- `review/` 保存审稿记录、候选对比、分支采纳结论和发布检查。

## GitHub 同步边界

这个仓库适合作为 GitHub repo 保存：

- 工作区规则、项目规则、长期文档和索引。
- 工具源码、README、schema、测试和可复用脚本。
- Prompt 文件、生成配方、production ledger、review decisions 和 media manifest。
- 小型 SVG、示意图、Markdown、JSON、CSV 和可复现配置。

默认不把以下内容放进 Git：

- 大型图片、视频、压缩包、缓存和临时下载。
- 单个项目中尚未筛选的海量候选稿、临时生成结果和无索引输出。
- 本机绝对路径、密钥、token、cookie、账号凭据和未脱敏外部链接。
- 可通过账本、manifest、prompt 或外部资料库恢复的大体积派生产物。

大型媒体或临时输出建议由 Media Vault、网盘、Syncthing、Resilio、rclone 或其他同步方式管理；Git 中只保留路径、hash、用途、生成配方和筛选结论。

## AI 生产记录

正式生产结果应尽量记录：

- 任务目标：设定整理、章节续写、润色、重写、分支试写、发布整理或临时参考。
- 输入参考：原文、设定、角色卡、伏笔表、时间线、风格指南和外部参考资料。
- 生成配方：prompt、模型、参数、seed、版本差异和提交命令。
- 输出路径：优先使用项目相对路径。
- 审稿结论：selected、rejected、needs_review、deprecated 或其他项目约定状态。
- 下一步动作：返工、扩展、入库、上屏、交付或归档。

## 多窗口协作

推荐把复杂项目拆成多个协作窗口：

- 设定窗口：整理世界观、角色、阵营、场景、道具和视觉规则。
- Prompt 窗口：把写作目标转成模型可执行的续写、润色、改写或审稿 prompt。
- 生成窗口：调用文本生成、拆章、替换或整理工具，记录输出和生成配方。
- 审稿窗口：对比候选稿、标记可用版本、记录否决原因和返工方向。
- 写作窗口：处理剧情、章节、角色台词、伏笔回收和交接文档。
- 工具窗口：维护索引、账本、同步规则、脚本和自动化流程。

这些窗口共享文件事实层，不依赖某一个聊天窗口长期保存全部上下文。

## 项目阅读入口

每个项目都需要同时保留两类入口：

1. 给 Agent 读的工作入口：`AGENTS.md`、`PROJECT.md`、`WORKFLOW.md`、`_pipeline/`。
2. 给人类读的项目纲要：项目根目录下和 `PROJECT.md` 同级的 `<project-name>_project-brief.html`。

人类项目纲要必须是静态 HTML，重点回答：

- 这个项目是干什么的。
- 当前有哪些核心资产。
- 从哪里查看配置、prompt、输出和审稿结果。
- 当前整理状态和下一步建议。

如果项目目标或项目作用发生变化，必须同步更新这份 HTML 纲要。

## 后续 GitHub 接入

等 GitHub 仓库地址确定后，建议补充：

- 远程仓库地址和默认分支。
- 每日同步流程。
- 哪些目录默认纳入提交。
- 哪些目录进入 `.gitignore`。
- 大型媒体的外部同步方案。
- 提交前检查命令和人工检查清单。

## 语言和命名规则

- 文件名、目录名、脚本名和稳定资产名优先使用英文。
- Markdown 正文、制作说明、审稿结论和交接记录默认使用中文。
- 中文 Markdown 使用 UTF-8。
- 不为了形式做中英双写；只有模型提交、外部协作或明确需求需要时才写英文。
