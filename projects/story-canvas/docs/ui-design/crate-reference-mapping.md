# CRATE 参考到 Story Canvas 的映射

## 来源与边界

参考来源：

- CRATE 产品入口：`https://crate.tiktok-row.net/`
- 用户提供的飞书 Wiki 教学文档：`https://bytedance.larkoffice.com/wiki/Q9eDwXIIsijPcRkzjHScpvmXnXd`
- 用户提供的 CRATE 用户使用手册：`https://bytedance.sg.larkoffice.com/docx/Lo1qdQEFFoYwS2x2RySlu5Dsgsg`
- 公开补充资料：ByteDance Seedance、AI infinite canvas 产品文章和公开无限画布工具对比。

公开搜索没有找到可稳定引用的 CRATE 产品说明页，`Type9` 的精确公开结果也不足以作为事实来源。因此 CRATE 的功能细节以用户提供的飞书 Wiki 为准，公开资料只用于补充同类产品趋势。

CRATE 是以图片、视频和多模型资产生成为中心的无限画布工具。Story Canvas 不能直接复制它的产品结构，因为我们的核心对象不是图片资产，而是长篇小说的主线、章节、分支、伏笔、设定变化和候选正文。

可借鉴的是交互方式、低噪声 UI、节点化生成、参考材料槽位、候选版本管理和多步派生流程。不可借鉴的是把 Text / Image / Video 作为同等第一层对象。Story Canvas 的第一层对象必须是故事结构，图片和视频是从故事节点派生出来的表达资产。

## 公开资料补充结论

- ByteDance Seedance 的公开说明强调文本/图片到视频、多镜头叙事、主体和风格一致性、复杂动作与镜头运动控制。这支持 Story Canvas 后续把视频节点设计成“从章节或场景派生的镜头链”，而不是孤立的视频按钮。
- AI infinite canvas 类产品的公开文章反复强调同一点：画布必须让 AI 读懂节点内容、连接关系和上下文，否则只是摆满卡片的白板。
- 面向写作或研究的 AI 画布通常强调把生成文本、提纲、参考资料和提示词留在同一空间，并通过连线控制上下文。这与我们的章节节点、草稿节点、候选版本、参考范文和故事卡路由一致。
- 公开无限画布工具对比里，AI-aware canvas、local-first Markdown/JSON、结构化卡片、可读上下文是高频方向。Story Canvas 应优先保持本地文件事实层和结构化节点，而不是追求视觉白板的自由堆放。

## CRATE 可借鉴能力

### 用户手册确认的产品概念

CRATE 手册把平台拆成以下核心对象：

| 概念 | CRATE 含义 | Story Canvas 映射 |
| --- | --- | --- |
| `Projects` | 项目文件，一个项目内包含多个模块，可复制、重命名、删除、分享 | 一个作品/章节工作区，不直接等同仓库项目 |
| `Canvas` | 创建和管理模块的无限画布，支持缩放、平移、双击加模块 | 章节、草稿、设定和媒体 brief 的主工作面 |
| `Blocks / Nodes` | Text、Image、Video 等生成模块 | 章节节点、草稿节点、故事卡节点、媒体派生节点 |
| `Prompt` | 每个模块的生成输入，直接影响结果 | 用户方向、重构框意见、生成 brief 和 prompt_goal |
| `Connect` | 模块连接后，下游自动读取上游文字或图片 | 节点依赖和上下文引用，必须可追踪 |
| `Models` | 不同模块可选择不同生成模型 | Agent / 模型选择字段 |
| `Advanced Settings` | 模型参数、尺寸、负面提示词、input_fidelity 等 | 高级生成参数，默认折叠 |
| `Toolbar` | 新建、历史、模板、帮助、分享等入口 | 低噪声工具栏，保留图标入口 |
| `History` | 可找回删除或覆盖模块，但连接上下文会丢失 | 历史快照必须保存节点与连线，避免只恢复孤立文本 |
| `Template` | 已沉淀的可复用工作流 | 章节生成/检查/媒体 brief 的可复用流程模板 |
| `Group` | 圈选多个模块成组，可命名、改色、一键生成 | 篇章、场景组、候选组或批量生成单元 |
| `Stickys` | 只做文字说明和备忘，不具备生成能力 | 画布批注、审稿意见、人工提醒，不进入生成规则 |
| `Agent` | 右侧输入需求，自动分析、整理并生成多类型节点 | 故事任务编排器，负责把用户意见拆成上下文读取、生成、检查和候选保存 |
| `Multi Layers Edit` | 图片拆层和局部调整 | 场景镜头分层、媒体资产精修，不改故事事实层 |

这些概念说明 CRATE 的核心不是单个按钮，而是“节点 + 连接 + 历史 + 工作流 + Agent”的组合。Story Canvas 应保留这个组合，但把第一对象从视觉资产换成故事结构。

### 项目与画布

- 项目首页提供清晰的创建入口。
- 画布中通过 `ADD NODE` 增加节点，常见类型包括 Text、Image、Video 和 Multi-layer。
- 节点是生成动作的最小容器，节点内放提示词、参考图、模型和输出。
- 生成通常一次产出多个候选，用户从候选里挑选继续迭代。
- 空白画布支持双击快速添加模块。
- 项目内的复制、重命名、分享和删除都属于项目文件管理，不应混入节点生成逻辑。

### Text 节点

- Text 节点可用于提示词优化。
- 可接 Qwen、DeepSeek 等模型，把用户粗略想法整理成更可执行的提示词。
- 对 Story Canvas 的启发：网页端的重构框、续写方向框、媒体 brief 框，都应该允许“只优化指令，不直接生成正文”。
- CRATE 当前 Text 节点主要面向视觉提示词优化，不是通用文本创作。Story Canvas 不能照搬这个限制；我们的文本节点需要承载章节、梗概、重构意见、故事卡和媒体 brief。

### Image 节点

- Image 节点支持参考图、提示词、比例设置、生成、局部修改、背景移除、放大和分层。
- 参考图可以承担不同用途，例如角色、动作、构图、材质、风格、场景布局。
- 复杂任务需要明确每张参考图的作用，避免模型把角色参考、姿势参考和风格参考混在一起。
- 对 Story Canvas 的启发：未来图片节点不应该只是上传图片，而要标注参考类型。

### Video 节点

- Video 节点可从图片和提示词生成动作过程。
- 视频适合表达动作变化、镜头运动、角色状态变化和关键场面的动态版本。
- 对 Story Canvas 的启发：视频节点应当从章节、场景或镜头 brief 派生，而不是独立漂浮。
- 手册确认视频尺寸通常跟随连接的图片模块；这提示我们的视频 brief 要显式继承上游图片或场景的画幅、角色和构图约束。

### Multi-layer 节点

- Multi-layer 适合把画面拆成前景、中景、背景或局部层。
- 对 Story Canvas 的启发：长篇工具里可对应“场景镜头分层”，例如角色层、环境层、道具层、气氛层、动作层。

### 连接与历史

- CRATE 的连接线会让下游模块读取上游文字或图片，因此连接是上下文协议，不只是视觉连线。
- 删除连接后，引用素材或文字仍保留，但节点关系断开。
- CRATE 的 History 可找回删除或覆盖模块，但连接上下文会丢失。
- Story Canvas 的历史设计应反过来加强这一点：恢复草稿、章节或媒体 brief 时，必须尽量恢复节点位置、route mode、上下游锚点和连线关系，不能只恢复孤立文本。

### 模板、群组和批量运行

- CRATE 模板工作流可以把沉淀好的节点流程加入画布，用户替换图片或提示词后点击 `Run` 一键生成。
- CRATE 群组可圈选多个模块，支持命名、改色和一键生成。
- Story Canvas 可把这两者映射为：三章剧情单元模板、十章篇章检查模板、章节续写模板、分支试写模板、媒体 brief 模板，以及“批量生成/批量检查”的节点组。

### 贴纸与批注

- CRATE 贴纸只用于说明、记录和画布管理，不具备生成能力。
- Story Canvas 也应区分“批注/提醒”和“生成请求”。批注可以辅助人类协作，但不能自动进入 prompt，除非用户明确把它提升为生成意见。

### Agent 与 CLI

- CRATE Agent 在右侧打开，用户输入详细需求后，Agent 自动分析、整理并生成结果，适合重复或多步骤生成任务。
- CRATE CLI 面向 Claude Code、Cursor、Codex、Gemini CLI 等 Agent 环境，说明其生成链路不必完全依赖浏览器 UI。
- Story Canvas 后续的 Agent 面板应服务故事任务编排：读取相邻章节、整理用户指令、选择模型、生成多个候选、保存账本、检查衔接。浏览器只负责记录和展示，实际生成可以交给 Story Engine 或 CLI runner。

### 提示词经验

- 抽象词容易被误解，例如“梦幻”“高级”“精致”会被模型翻译成烟雾、虚化、光斑等默认视觉符号。
- 更稳定的写法是把抽象审美拆成可观察约束，例如低饱和、柔光、长焦、浅景深、强侧光、留白、边缘干净、不要新增背景。
- 如果主体不清晰，可以先用圈选、箭头、裁剪或遮罩明确修改区域，再移除辅助标记。
- 比例、构图和不变范围要明确写出，例如固定 16:9、角色比例不变、服装不变、背景不变。

### 多角色与场景经验

- 多角色生成要拆成角色槽位，逐个绑定角色参考、动作、位置和不能变的特征。
- 复杂图可以分块、裁剪、标注，再统一光照和氛围。
- 场景设计可按“效果图 -> 室内设计图 -> 多角度概念 -> 外观/街景/远景”的链路展开。
- 对 Story Canvas 的启发：一章可以派生多个媒体 brief，但它们必须回指同一个故事节点和同一组设定约束。

## Story Canvas 的节点体系

### 第一层故事节点

这些节点是 Story Canvas 的主对象：

- `story-mainline`：作品主线或卷主线。
- `chapter`：正式章节节点。
- `chapter-part`：同章内部上/中/下或剧情段。
- `draft-branch`：从某章拖出的独立分支草稿。
- `draft-interstitial`：插在相邻两章之间的过渡草稿。
- `scene`：章节内关键场景。
- `character-state`：角色状态变化表。
- `foreshadowing`：伏笔、回收点、误导点。
- `setting-delta`：设定增量。

### 第二层派生节点

这些节点不抢主线位置，只从故事节点派生：

- `media-brief`：把章节或场景转换成图片/视频需求。
- `image-generation`：图片生成节点。
- `video-generation`：视频生成节点。
- `multilayer-shot`：分层镜头或分层场景节点。
- `visual-reference`：角色、动作、风格、材质、场景布局等参考材料。
- `prompt-optimization`：只优化指令或提示词，不直接产出正文。

## 边与路线语义

Story Canvas 的连线要表达故事关系，不只是视觉连接。

| 关系 | 含义 |
| --- | --- |
| `continues` | 正式章节连续承接 |
| `branches` | 从某章分出试写路线 |
| `inserts-between` | 插入两章之间，服务上下文过渡 |
| `depends-on` | 依赖某个设定、伏笔或角色状态 |
| `candidate-of` | 某候选属于某章节、段落或草稿 |
| `selected-for-mainline` | 候选已被确认进入主线 |
| `uses-reference` | 使用某个参考材料 |
| `adapts-to-media` | 从故事节点派生成图片、视频或镜头 brief |
| `reads-context-from` | 下游生成读取上游节点内容 |
| `group-runs-with` | 多个节点作为同一工作流或批量任务运行 |

## 生成意图优先级

当 Story Canvas 触发续写、重构、拆章、分支生成或媒体 brief 时，解释顺序应为：

1. 当前任务里用户最新明确指令。
2. 网页端当前节点、选区或重构框里的直接意见。
3. 节点锚点、前后章节、route mode、目标字数、拆章数和候选版本数。
4. 项目的长篇生成规则、章节治理规则、故事卡结论和参考范文学习结果。
5. 跨项目方法论和通用写作建议。

这意味着：网页端重构框里的具体意见优先于此前从故事卡或范文中学到的通用经验。通用经验只用于补足判断、检查衔接和避免失控，不能覆盖用户对当前节点的明确要求。

## 右侧面板简化

建议把右侧面板固定成四个短标签：

- `故事`：正文摘要、章首承接、章尾钩子、角色状态、伏笔和设定增量。
- `生成`：Agent、模型、版本数、目标字数、拆章数、用户方向、记录生成请求。
- `媒体`：从当前节点派生图片、视频、分层镜头和参考材料。
- `历史`：候选、快照、账本、撤销恢复，并显示本节点恢复时是否保留上下游连接。

高级字段默认折叠。用户常用操作只保留：选择 Agent、填方向、设字数、设版本数、设拆章数、记录请求、拆章、删除草稿。

### 2026-06-29 已落地到网页端

- 顶部画布只保留当前节点路径和缩放状态，缩放、重置和整理布局移到底部低噪声 dock。
- 右侧栏增加“故事 / 文本或生成 / 历史”的短标签跳转；正式章节显示“文本”，草稿节点显示“生成”。
- 草稿节点在画布卡片上直接显示 Agent、模型、版本数和目标字数，让节点更像可追踪的生成任务。
- 草稿右栏增加上下文连接条：`interstitial` 显示上游和下游章节，`branch` 显示上游和独立分支路线。
- 草稿“开始生成”会把 Gemini 候选正文直接物化成多个画布草稿版本节点，而不是只压在右栏候选列表里。
- 草稿生成和拆章按钮增加转圈处理中状态；拆章结果用半透明虚线容器包住内部草稿段，借鉴 CRATE 的 group 语义，同时保留“未确认”状态。

## 空画布与工具栏

CRATE 的中心 `ADD NODE` 可以借鉴，但 Story Canvas 的默认入口应改成故事优先：

- 添加故事节点。
- 添加分支草稿。
- 添加媒体 brief。

图片、视频和多层节点不应在第一屏占据同等权重。它们应从章节、场景或媒体 brief 中派生。

工具栏尽量使用图标按钮，悬停显示说明。常驻文字只保留路径、保存状态、当前选中节点和必要错误信息。

画布空白处可支持双击快速添加节点，但默认弹出的节点类型应以故事为先：章节、分支草稿、插入草稿、故事批注、媒体 brief。图片和视频节点只在媒体 brief 或场景节点上下文中作为二级入口出现。

## 媒体 brief 字段建议

媒体节点未来可用以下字段，作为生成层和外部图片/视频工具的桥接信息：

```text
node_type:
source_story_node_id:
source_project:
source_file:
source_anchor:
media_role:
prompt_goal:
reference_assets:
subject_anchor:
reference_scope:
style_reference:
must_keep:
must_not_add:
aspect_ratio:
output_count:
model:
candidate_versions:
selected_version:
ledger_ref:
created_at:
```

其中 `reference_assets` 每项建议包含：

```text
asset_path:
asset_type:
reference_role:
scope:
notes:
```

`reference_role` 可使用：

- `character`
- `pose`
- `composition`
- `style`
- `material`
- `layout`
- `lighting`
- `mask`

## 多角色画面字段建议

多角色图片或视频 brief 需要显式角色槽位：

```text
role_slots:
  - character_id:
    display_name:
    reference_asset:
    crop_or_mask:
    position:
    action:
    must_keep:
    must_not_merge_with:
```

这个结构用于避免生成层把多名角色融合、错换服装或遗漏关键动作。

## 场景派生链路

章节或场景节点可派生以下媒体链路：

1. `scene-brief`：从正文提取场景目标、角色、冲突、情绪和关键物。
2. `layout-concept`：场景布局、空间关系和视角。
3. `image-concept`：单张概念图。
4. `multilayer-shot`：前景、中景、背景、角色、道具分层。
5. `video-shot`：镜头运动、角色动作和时间变化。
6. `selected-media`：确认可作为项目视觉参考的版本。

每一步都必须回指原章节或场景，不能让媒体生成反向改写故事事实层，除非用户明确确认。

| P2 | 参考材料槽位 | 标注角色、动作、风格、构图、材质、布局等用途 |
| P2 | 抽象词具体化助手 | 把“高级、梦幻、精致”等词转成光线、镜头、比例和不变约束 |
| P2 | 多角色槽位 | 角色逐个绑定参考、位置、动作和不混淆规则 |
| P3 | CLI runner | 把网页生成请求交给 Story Engine / Codex / Claude / DeepSeek 等 runner |
| P3 | 图片/视频 provider runner | 后续再接具体图片、视频模型或外部工具 |
| P3 | 多层镜头节点 | 等媒体 brief 稳定后再做，不提前复杂化 |

## 设计原则

- Story Canvas 是故事架构画布，不是图片生成器换皮。
- 所有媒体节点都要能追溯到故事节点。
- 所有候选都默认不写回主干，必须经过选择。
- 用户当前写在网页端的具体意见，比旧规则和参考范文更优先。
- UI 越靠近写作主链路越简洁，越靠近媒体生成和高级调参越折叠。
