# 故事画布规则

## 项目默认结构

- 章节节点：每章一个节点，目标 3000 到 6000 字。
- 章节部分：同一章拆成上/中/下时，画布上仍是一个大章节节点，展开后显示内部部分。
- 剧情块：每篇文章内部按段落或标题切成编号块，用于局部选择和段落级 reroll。
- 大篇章：每 10 章一个篇章。
- 卷：每 5 个篇章为一卷，即 50 章。
- 卷核心方向：一卷内锁定，不能在未确认的情况下改变。

## 文件与 JSON 落点

- 每篇正文旁边维护同名 `.story.json`，例如 `第七章（上）.md` 对应 `第七章（上）.story.json`。
- `.story.json` 只保存剧情块编号、行号、hash、候选和同步状态，不复制整篇正文。
- 当前文件夹的节点位置和工作区状态保存到 `.story-canvas.folder.json`。
- 当前文件夹的操作账本保存到 `.story-canvas.ledger.jsonl`。
- 正文快照和 sidecar 快照保存到 `.story-history/`，用于回溯和恢复上一版。
- `_ledger/story-canvas/` 继续保存项目级画布索引、schema 和长期记录。
- 网页实时同步只负责刷新文件系统状态，不自动采纳候选；候选进入正文仍需明确确认。

## 层级边界

- 故事画布属于工具层，负责节点、选区、sidecar、候选状态、历史快照、生成请求和设定增量表的记录。
- 长篇生成规则、prompt 模板、章节质量门和生成后自检属于生成层，维护在 `docs/rules/longform-generation.md`、`prompts/` 和 `templates/`。
- 画布中的 `generation_settings`、`generation_requests`、`prompt_goal`、`user_directive` 和 reroll 目标只是桥接字段；它们提供用户意图和选区锚点，不承载完整生成规则。
- 修改网页工具、sidecar schema 或节点字段时，按 `layer-boundaries.md` 检查，不顺手修改生成规则或 prompt 模板。
- 修改生成规则或 prompt 模板时，不顺手改网页 UI、`.story.json` 结构或历史回滚机制。

## 节点必填字段

| 字段 | 说明 |
| --- | --- |
| 节点 ID | 稳定唯一标识，例如 `v01-a01-ch001` |
| 所属卷 | 例如 `v01` |
| 所属篇章 | 例如 `v01-a01` |
| 章节号 | 全局章节号 |
| 目标字数 | 默认 3000-6000 |
| 主线动作 | 本章推进主线的具体动作 |
| 分线动作 | 本章推进角色、秘密、伏笔或关系的动作 |
| 章首承接 | 接上一章尾部的具体点 |
| 章尾钩子 | 推下一章的具体点 |
| reroll 记录 | 候选版本、状态和结论 |
| 剧情段 reroll | 章内段落级候选版本和替换状态 |
| 设定增量表 | 本章人物、环境、剧情节点和通用设定变化 |

## 续写草稿节点

| 字段 | 说明 |
| --- | --- |
| `route_mode` | `interstitial` 表示插入相邻章节之间；`branch` 表示独立分支路线 |
| `after_group_key` | 草稿承接的上一节点 |
| `before_group_key` | 插入草稿的下一节点；分支草稿可为空 |
| `branch_from_group_key` | 分支来源节点 |
| `generation_settings.agent` | 计划使用的 Agent 或文字模型，例如 Trae 主模型、Codex/GPT-5、Claude、DeepSeek、Gemini 3.5 Flash 或手动填稿 |
| `generation_settings.version_count` | 计划生成的候选版本数 |
| `generation_settings.target_chars` | 计划字数；正式统计仍用工作区 word-count 工具 |
| `generation_settings.split_count` | 1 到 4，表示保留一段或拆成多个草稿章节 |
| `generation_settings.prompt_goal` | 用户在网页端写入的续写/分支/插入方向 |
| `generation_batch` | 已生成版本节点的批次信息，包含来源草稿、请求 ID、候选版本 ID、当前版本序号和总版本数 |
| `status` | 草稿筛选状态：`draft` 待处理，`selected` 已采纳为生产候选，`rejected` 已放弃，`archived` 已从画布归档 |
| `decision_note` | 采纳、放弃或恢复草稿的原因 |
| `decided_at` | 最近一次版本决策时间 |

- 从章节节点边缘小圆点拖出的草稿，如果落在第 4 章和第 5 章之间，可视为第 4.5 式插入节点；未进入中间区域时，默认是独立分支。
- 插入节点服务上下文衔接和章节过渡；分支节点服务试写、平行路线或不同选择，不自动改主干。
- 生成请求必须写入 `generation_requests` 和账本，不能只留在网页临时状态；Gemini 直接生成成功时，候选正文必须物化为画布草稿版本节点，而不是只藏在右栏候选列表。
- Gemini、OneAgent Claude 和 Ark DeepSeek 多版本生成应并发执行，并在网页端显示处理中状态；失败时必须把错误留在当前草稿面板状态区，不能静默失败。
- Codex / GPT-5 生成请求必须写入 `.story-canvas-codex-bridge/` 桥接任务队列和账本；除非有明确的 Codex App/CLI 消费者接管，不得在网页端宣称已经生成完成。
- 生成后的多个草稿版本必须支持显式筛选：用户可标记采纳、放弃或恢复草稿。采纳只改变候选状态，不自动覆盖主干正文、人物卡或发布稿；同批次其他候选可标为放弃但文件仍保留。
- 草稿节点不使用正式章节、部分或剧情块的反馈重Roll框；草稿阶段的修改意见写入 `generation_settings.prompt_goal` 或新的 `generation_requests`。
- 拆章后的子草稿继承原草稿生成设置，并记录来源草稿 ID；网页端必须用半透明虚线大框包住子草稿，表现为未确认的草稿章节组，子草稿仍需用户确认后才能进入主干。
- 选中草稿节点按 `Delete` 只归档草稿节点并移出画布；正式章节节点不得被 Delete 删除，草稿正文文件默认保留。

## 设定增量表

每个章节节点至少维护四类增量表：

### 角色变化表

| 角色 | 本章新行为 | 状态变化 | 关系变化 | 新秘密/信息 | 人物卡同步 | 来源版本 |
| --- | --- | --- | --- | --- | --- | --- |

人物卡同步状态建议使用：

- `pending`：本章变化待同步。
- `synced`：已写入人物卡。
- `branch-only`：只属于分支或候选版本。
- `rejected`：对应 reroll 被否决，不进入人物卡。

### 环境设定表

| 环境/场景 | 本章新增细节 | 状态变化 | 可复用限制 | 设定同步 | 来源版本 |
| --- | --- | --- | --- | --- | --- |

### 剧情节点表

| 剧情节点 | 本章进展 | 主线影响 | 分线影响 | 后续依赖 | 同步状态 |
| --- | --- | --- | --- | --- | --- |

### 通用设定表

| 类型 | 名称 | 本章变化 | 影响范围 | 同步目标 | 同步状态 |
| --- | --- | --- | --- | --- | --- |

类型建议：世界规则、道具、组织、地点、关系规则、伏笔、时间线。

## Reroll 规则

- 节点 reroll 只生成候选，不覆盖 selected。
- 用户在网页重构框中写入的意见是当前选区、部分或整章的直接指令；工具层负责稳定记录，冲突优先级由生成层按 `layer-boundaries.md` 和对应生成规则解释。
- 用户后续在聊天或任务中给出的新意见优先于已保存的网页重构框意见。
- 每个 reroll 必须说明和上一版的差异。
- reroll 产生的新设定变化先进入节点表，不自动进入稳定设定文件。
- selected 版本变化确认后，才按人物卡工作流同步。

## 剧情段 reroll

- 章内任意段落可以作为剧情段独立 reroll。
- 剧情段必须保存选区锚点，例如剧情块编号、段落号、起止字符位置、原文短引或前后文短引。
- 剧情段候选只替换该段，不得覆盖整章。
- 未确认前，候选版本只留在段落 reroll 表。
- 应用候选后，检查本段前后两段衔接、角色状态、环境设定和字数统计。
- 如果网页重构框意见与故事卡或长篇生成规则冲突，由生成层按用户具体意见执行，并在生成说明中标出冲突；工具层不得用 UI 文案或 schema 静默改变生成规则。

## 篇章节奏建议

每 10 章篇章可以默认采用：

- 第 1-3 章：建立阶段问题。
- 第 4-6 章：加压和误导。
- 第 7-9 章：正面冲突和选择。
- 第 10 章：阶段回收，并抛出下一篇章钩子。

这个结构服务稳定推进，不是死板模板；但偏离时需要在规划里说明原因。
