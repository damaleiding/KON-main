# 章节治理规则

## 目标

章节治理用于确定“哪些文本算一章、怎么拆分、怎么命名、怎么合并、怎么承接前后文”。它服务长篇写作的可追踪性，不服务临时聊天里的口头方便。

## 章节单位

- 单章默认目标长度为 3000 到 6000 字，统计口径按工作区默认的非空白 Unicode 字符数；具体平台要求可覆盖，但必须注明。
- 一章应有明确叙事功能：引入、推进、转折、揭示、回收、缓冲或收束。
- 一章可以拆成上/中/下或多部分，但每个部分仍应有独立的场景推进和尾部承接点。
- 不因单次生成长度随意改章节编号；拆分和合并必须留下来源和版本记录。
- 标题、编号和文件名应稳定、可排序、可脚本处理。

## 命名建议

```text
01_第一章：章节标题.md
02_第一章：章节标题（中）.md
03_第二章：章节标题.md
00_章节索引.md
```

- 文件名前缀优先使用两位或三位数字，保证排序稳定。
- 标题变更时，同步检查章节索引、发布稿、账本和引用路径。
- 如果已有作品使用既定命名规则，优先遵守作品内既定规则。

## 拆章规则

- 拆章前先确认来源版本、拆分目标、每段叙事功能和是否影响发布稿。
- 拆分后每个新文件都应能独立说明：来源、范围、上一段承接、下一段悬挂点。
- 不把同一段正文同时保留在多个主干文件中；如需保留候选，放入 `分支/`、`outputs/` 或 `_ledger/` 指定位置。
- 拆章涉及正文覆盖时，先执行项目备份工作流。

## 合并规则

- 合并前确认主干版本、分支来源、采纳范围、被替代文本和冲突设定。
- 合并后检查章节编号、标题、首尾承接、字数统计和发布稿来源说明。
- 分支内容进入主干前，应记录来源、采纳范围和被替代内容。

## 局部扩写治理

- 局部扩写属于正文修改；开始前应确认源文件、目标段落范围、扩写目的、允许改动范围和不可改事实。
- 扩写目标应写成叙事功能，例如“补齐递物动作链”“增加试探与误解”“让伏笔被角色注意到”，不只写“加长”。
- 新增内容必须能嵌回原章节首尾关系；不得因为局部扩写破坏上一段的承接或下一段的触发。
- 扩写后如果单章长度明显超出目标范围，应评估是否拆分、移入分支稿或只采纳局部节点。
- 采纳扩写时，应记录来源版本、采纳范围、被替代文本、字数变化和需要同步的章节索引或账本。

## 首尾检查

章节生成、润色、拆分、合并或发布整理后，必须检查相邻章节：

- 上一章尾部：是否留有可被下一章接住的动作、物件、声音、状态、问题或人物反应。
- 下一章开头：是否接住上一章尾部，而不是复述上一章已经完成的动作。
- 状态继承：下一章是否继承上一章至少一个具体状态，例如信息、资源、关系、风险、物件、承诺、误会或伤害。
- 章尾交付：章尾是否留下下一章能直接执行或验证的动作、物件、决定、约定、风险窗口或信息缺口。
- 过渡锚点：跳时、换地、换视角时是否有足够清晰的时间/地点/人物锚点。
- 信息节奏：章尾不硬总结，章首不大段补设定。
- 四账本：信息、资源、关系、风险是否至少一项变化；若都不变，该章可能空转。
- 伏笔状态：尾部新埋线索是否进入伏笔表或待同步清单。

## 章节确定流程

1. 读目标作品轻量入口、章节索引和必要相邻章节。
2. 如果是写作前规划，先按 `plot-and-chapter-planning.md` 确认三章单元、主线、分线和字数目标。
3. 判断本次是新增、续写、拆分、合并、重命名还是发布整理。
4. 列出输入版本、输出路径、影响章节和需要同步的索引。
5. 修改正文前执行备份；纯规划只输出方案。
6. 修改后更新字数统计、章节索引、账本或待同步项。
